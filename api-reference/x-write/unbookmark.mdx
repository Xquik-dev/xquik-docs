## Remove one bookmark by Tweet ID

Put the exact Tweet ID in the request path.
Put the connected account username or ID in the body.
That account loses the bookmark.

This endpoint accepts 1 Tweet ID per request.
It never deletes the tweet, likes, or reposts.

## Clear many bookmarks

Read the saved posts with [Bookmarks](/api-reference/x/bookmarks).
Send 1 request per Tweet ID with its own `Idempotency-Key`.
Keep each removal in your ledger before the next request.

Show the account owner the posts before the removal starts.
Removed bookmarks don't come back unless the account saves them again.

## Save a removal receipt

| Removal column    | Source                 | Rule                                       |
| ----------------- | ---------------------- | ------------------------------------------ |
| `acting_account`  | Request `account`      | Match the account that saved the bookmark. |
| `tweet_id`        | Path `id`              | Keep the exact bookmarked Tweet ID.        |
| `idempotency_key` | Request header         | Create a fresh key for each removal.       |
| `write_action_id` | Response `id`          | Store the removal action.                  |
| `terminal`        | Response `terminal`    | Change the local list only when `true`.    |
| `safe_to_retry`   | Response `safeToRetry` | Retry only when this value is `true`.      |

## Twitter remove bookmark API questions

### Can an API remove a bookmark by Tweet ID?

Yes. Send the Tweet ID in the path and the connected account in the body.

### How do I remove all bookmarks?

Page through [Bookmarks](/api-reference/x/bookmarks), then remove each post with this route.
Each removal costs 10 credits.

## Handle errors

Never infer failure from a client timeout.
Poll a returned action before sending another request.

- For `400`, correct the Tweet ID or account value.
- For `401`, replace invalid Xquik authentication.
- For `402`, add credits before another request.
- For `403`, reconnect the selected X account.
- For `409`, keep the original action and payload.
- For `422`, review the X rejection before retrying.
- For `429`, wait for `Retry-After`.
- For `500` or `503`, follow `safeToRetry` and `terminal`.
